# Venue - one-page summary

Venue is a compliant secondary market for tokenised real-world assets. Cleanverse Verified Identity shapes the order book before a trade is formed, and Cleanverse Verified Assets settle both legs atomically on Monad.

- Live demo: https://venue-rwa.fly.dev/
- Public repo: https://github.com/brutaldevvin/venue
- Machine-readable proof: https://venue-rwa.fly.dev/api/health
- Raw projected books: https://venue-rwa.fly.dev/api/state
- Settlement ledger: https://venue-rwa.fly.dev/api/ledger
- Deployed chain: Monad testnet, chainId `10143`

## Problem

Tokenising a real-world asset is solved. Selling one is not. Private credit, fund shares, and other restricted assets need counterparties whose eligibility is known before a trade is formed. The usual pattern is to let anyone place an order and rely on a transfer revert at the end. That creates settlement breaks, gas waste, and information leakage: showing ineligible liquidity, even greyed out, still leaks the book.

## Solution

Venue moves compliance into market structure. The same asset renders as different order books for different viewers because each book is projected against live Cleanverse identity data. An eligible institution sees depth. A credentialed but lower-tier viewer sees an empty book with the governing rule. An unverified viewer receives the registry verification path.

The matcher checks eligibility at match formation, before value moves. If a pair would fail the rule set or a venue-side limit, that pair is never formed. Settlement still re-verifies on-chain, so the venue can hide or skip liquidity, but it cannot force a bad transfer through settlement.

The signature demo case is a full holder cap. A better-priced bid from a new holder is passed over for a worse bid from an existing holder. Price-time priority is deliberately subordinated to a disclosed compliance term, and the tape names the rule that caused the skip.

## Cleanverse integration points

**CVI.** Demo credentials are real A-Passes issued through `generate_apass` and read live through `query_apass`. The three viewer states are operationally distinct: sub-tier 75 and eligible, sub-tier 9 against a rule requiring 70, and no A-Pass. The lapse button calls `update_status` at the registry, and a watcher removes the affected maker's resting orders from the book. The unverified viewer path comes from `verify_apass`.

**CVA.** Both settlement legs are CVA-aware. The cash leg is Cleanverse aUSDC at `0xaC0893567D43C3E7e6e35a72803df05416C1f20D`, which enforces CVI on transfer. The security is a Cleanverse registered asset at `0x3b4ef029bef7750f6f8ce81986e51f539ac389de`. Delivery-versus-payment settles security and cash in one transaction through `0xea5e891232850b6d3b8822e9883ae81586351f4c`; the settlement contract is never the sender or recipient of either leg.

**CCP / RuleV2.** Rules are read from the Cleanverse validator at `0xaC7e5179C2C7f03f209136886c172eb34F161792`. The implementation handles the complete `RuleV2` shape confirmed by the Cleanverse team: `allowedGroup`, `allowedSubGroup`, `minTier`, `minSubTier`, `isBlackList`, and `countryBitmap`. The deployed validator exposes `getRulesV2` but not `canTransfer`, so Venue gates against an `IATokenPolicy`-compatible policy instance at `0x2c6e4819cf4bb4a355f5b29903cff44053e5ebff`; the policy is a constructor argument so it can be repointed without code changes.

## Demo path

Open the live app. Before clicking anything, compare the three viewer panes: one asset, three CVI states, three different books. Press **two bids cross** to see the holder cap bind and a fill settle. Press **a credential lapses** to freeze a maker's A-Pass and watch the watcher pull their orders. Press **reset** to restore the registry and book.

## Evidence

`/api/health` reports the current Monad block, CVI registry reads, configured contracts, holder cap, settlement-agent gas, and cash-leg asset check with `cache-control: no-store`. `/api/state` returns the exact projection rendered by the UI. `/api/ledger` rechecks settlement receipts at request time. `EVIDENCE-RUN.md` is generated by `scripts/capture.ts` and includes transaction hashes confirmed by receipt.

Validation includes 23 Foundry contract tests, a 256-run transfer-policy fuzz, 60,000 property cases over two invariants checked against an independent policy oracle, and a differential test that runs the matcher against deployed contracts and settles every pair it forms.
